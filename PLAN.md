## What this is

A Maryland grid-stress early-warning and daily conditions brief, built on public data, that **keeps receipts on every forecaster — including PJM and itself**. Core question: *is tomorrow a high-stress day for the grid, and when the day lands, who called it right?*

- **Public good is the framing.** Peak days are when the dirtiest peaker plants run and when outages hurt the most vulnerable people hardest. Nothing in this project has anything to do with EV charging; the money framing is gone (price survives only as a secondary line where it happens to be relevant).
- **Audience: whoever can use it** — Darren's household first, public readers welcome (Darren's correction, Oct 29, 2026). The binding constraint is **effort, not audience**: the brief stays a lightweight static page, and deployment (decision 4) is how it reaches people beyond the household at ~zero ongoing effort. No accounts, no actuation, no user-hunting, no heavy front-end build.

## Purpose horizons

- **Tier 2:** Junior Data Engineer / ETL evidence — the pipeline itself: multiple public APIs, incremental/idempotent loads, dbt models + tests, a forecast-scoring warehouse, freshness checks that complain instead of lying.

## Architecture (adopted from the proposal)

Chosen: **B's structure with A's single entry point** (proposal compared both; A's own critique flags its hand-synced schema).

- **dbt is the cleaning/feature layer only**: raw → cleaned (`eia_*`, `nws_*`, `ncei_bwi_daily_temps`) → `mart_day_history`. The warehouse is DuckDB locally; at S5 the same dbt project gains a Supabase (Postgres) deployment target per decision 4 — DuckDB stays the local/dev target, one project, two targets. Per decision 5 (Oct 30, 2026) the project also gains a Databricks target (Free Edition) as the cloud-warehouse proof target — one project, three targets.
- **Pure Python owns the judgment**: `stress` (forecaster), `scoring`, `brief` (rendering) — pure modules that import none of the IO modules, so tests drive them in milliseconds. **`ledger` is separate**: it is the IO owner of `ledger/`, its sole reader/writer — not a pure module.
- **One operational interface**: `grid daily` · `grid weekly` · `grid ledger verify`. `grid daily` runs fetch → `dbt build` → freshness → forecast → `ledger.append` → score settled days → render brief to `site/` → post as a comment on a pinned GitHub issue (notifies Darren; no email address or mail secret in the repo).
- **Receipts**: content-addressed JSON files under `ledger/forecasts/<forecaster_id>/<target_date>/`, hash in the filename certifying content, written exclusive-create. The receipt of record for a forecaster/date is the latest issued before that local day starts — a fixed rule, nothing to cherry-pick. **Stale inputs never skip silently**: they write a no-call receipt with a reason (`stale_load`, `stale_weather`).
- **Index definition**: versioned TOML (`ledger/definitions/stress-index-v1.toml`); **our** forecaster's receipts carry the definition's sha256 and its thresholds **frozen at issue time**, so an amended definition can never rescore an old call. External forecasters' receipts (e.g. PJM's, when it joins) carry `definition: null` — they don't forecast under our index; scoring compares their claims (peak MW, peak hour, level as issued) against actuals directly. Amendments add a new version file and a published `docs/index/<version>.md`; v1 is never edited.
- **Immutability, enforced**: `ledger verify` in CI as a required check and as a pre-commit hook; it scans the full git history for any non-add change under `ledger/`, any hash mismatch, any late issue. Branch protection blocks force-push. Commit dates can be forged; the GitHub push event is the third-party timestamp.
- **Geography honesty**: every receipt and brief states "PJM-wide call, Maryland weather." Scoring uses PJM RTO demand only. BGE is trailing display color (~47h lag), labeled, never blended into a claim.
- **PJM's official forecast as a scored forecaster**: still gated on the lawful route (gridstatus.io hosted API free tier — Darren's open sub-decision, unchanged). Structurally it is one new file (`forecasters/pjm.py`) when approved; the build does not block on it.

DuckDB stays the local/dev target and Supabase + Vercel stay the S5 deployment layer per decision 4 — Databricks is an additional target, not a replacement. Purpose, in Darren's framing: the project is a portfolio project and Databricks is what the industry asks for (29% of data-engineer postings in the Oct 30 demand check; Snowflake has no free tier — 30-day trial only — which is why Databricks carries this slot). Sequencing: the target is added after S3b verifies; S3b–S4 scope is otherwise unchanged.
6. **AWS added as a deployment target** — *Darren's explicit direction, Oct 30, 2026 (evening).* The pipeline gains an AWS deployment: **S3** as the data lake for the EIA/NWS/NCEI pulls, **Lambda + EventBridge** for the scheduled ingestion runs, **Athena** for SQL queries over the stored data, and the daily brief page hosted from S3.
